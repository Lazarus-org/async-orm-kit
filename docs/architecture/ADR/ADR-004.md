# ADR-004: QuerySet Compilation Architecture

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

Our Django-style API (ADR-002) collects query operations through method chaining (filter, exclude, select_related, etc.). We needed to decide how to transform this high-level API into SQLAlchemy constructs and ultimately SQL queries.

The query pipeline involves multiple stages: parsing user input, resolving fields and lookups, building conditions, and finally generating SQL. We needed to determine where each responsibility belongs and how components interact.

## Decision

We will implement a multi-stage query pipeline with clear separation of concerns:

1. **QuerySet:** Collects user operations via method chaining
2. **Filter Parser:** Parses Django-style field lookups (`field__lookup`)
3. **Field Resolver:** Resolves field names to SQLAlchemy columns, handling relationship traversal
4. **Condition Builder:** Constructs SQLAlchemy expressions from resolved fields and operators
5. **QueryState:** Stores all resolved expressions and query configuration
6. **QueryCompiler:** Transforms QueryState into final SQLAlchemy SELECT statement

The compiler acts as the final assembly stage, receiving pre-built expressions and wrapping them into appropriate SQLAlchemy methods.

## Rationale

**Why Multi-Stage Pipeline:**
- **Single Responsibility Principle (SOLID):** Each component has one clear job
- **Separation of concerns:** Parsing, resolution, and SQL generation are independent
- **Testability:** Each stage can be tested in isolation
- **Maintainability:** Changes to one stage don't affect others
- **Clarity:** Clear data flow from user input to SQL

**Why Compiler Receives Resolved Expressions:**
- Compiler focuses solely on SQL assembly, not expression construction
- Filter logic complexity is isolated in earlier stages
- Compiler can focus on query optimization and structure
- Easier to debug - can inspect QueryState before compilation

**Why Not Inline Everything:**
- Mixing parsing, resolution, and SQL generation creates tangled code
- Hard to test individual stages
- Difficult to optimize or modify one aspect without affecting others
- No clear point to inspect intermediate state

## Architecture

**Complete Query Pipeline:**
User API → QuerySet → Filter Parser → Field Resolver → Apply joins if needed → Condition Builder → QueryState → Compiler → SQLAlchemy → SQL


**Component Responsibilities:**

1. **QuerySet:** API surface, method chaining- `filter(age__gte=18)` → triggers parsing pipeline
   - Returns new QuerySet with updated state
   - Delegates to parser/resolver for expression building

2. **Filter Parser:** Parses lookup syntax
   - `"age__gte"` → `("age", "gte")`
   - `"author__profile__country"` → `(["author", "profile"], "country", None)`
   - Handles relationship traversal syntax

3. **Field Resolver:** Resolves to SQLAlchemy columns
   - `"age"` → `User.age` column
   - `"author__profile__country"` → `Profile.country` via join graph
   - Manages join graph construction for relationship traversal

4. **Condition Builder:** Constructs SQLAlchemy expressions
   - `("age", "gte", 18)` → `User.age >= 18`
   - `("email", "contains", "@example")` → `User.email.contains("@example")`
   - Maps lookup types to SQLAlchemy operators

5. **QueryState:** Stores resolved query configuration
   - Pre-built filter expressions (SQLAlchemy conditions)
   - Pre-built ordering expressions
   - Join graph with aliases
   - Annotations, aggregates, loading preferences
   - All expressions ready for SQL generation

6. **QueryCompiler:** Assembles final SQL statement
   - Receives QueryState with resolved expressions
   - Wraps expressions into SQLAlchemy methods
   - Applies query planning for loading strategies
   - Produces executable SELECT statement

## Compilation Process

**Phase 1: Expression Building (Before Compiler)**
```python
# User builds query
queryset = User.objects.filter(
    age__gte=18,
    email__contains='@example.com'
).select_related('profile').order_by('-created_at')

# Behind the scenes:
# 1. Filter Parser: "age__gte" → ("age", "gte")
# 2. Field Resolver: "age" → User.age column
# 3. Condition Builder: (User.age, "gte", 18) → User.age >= 18
# 4. QueryState stores: filters=[User.age >= 18, User.email.contains('@example.com')]
```

**Phase 2: Query Planning (Compiler Entry)**
```python
# Compiler analyzes QueryState
compiler = QueryCompiler()
stmt = compiler.compile(state)

# Planning phase:
# - Analyze join graph and query context
# - Decide loading strategies (joinedload vs selectinload)
# - Create LoadDirectives for each relationship path
```

**Phase 3: SQL Assembly (Compiler)**
```python
# Compiler wraps pre-built expressions:
stmt = select(User)  # Base SELECT
stmt = stmt.join(...)  # Apply JOINs from join graph
stmt = stmt.where(and_(*state.filters))  # Wrap filter expressions
stmt = stmt.order_by(*state.order_by)  # Apply ordering expressions
stmt = stmt.options(...)  # Apply loading options from directives
```

**Phase 4: Execution (SQLAlchemy)**
```python
# SQLAlchemy generates dialect-specific SQL
result = await session.execute(stmt)
users = result.scalars().all()
```

## Compiler Responsibilities

The compiler is **NOT** responsible for:
- Parsing field lookups
- Resolving field names to columns
- Constructing filter expressions
- Building condition operators
- Managing the join graph structure

The compiler **IS** responsible for:
- Receiving QueryState with pre-built expressions
- Query planning (loading strategy decisions)
- SQL statement assembly
- Wrapping expressions into SQLAlchemy methods
- Applying JOINs in topological order
- Configuring eager-loading options
- Handling different SELECT variants (values, values_list, only)
- Applying GROUP BY, HAVING for aggregates

## Code Structure

**QueryState (expression storage):**
```python
@dataclass
class QueryState:
    model: Type
    filters: List[ColumnElement]  # Pre-built: [User.age >= 18, ...]
    order_by: List[ColumnElement]  # Pre-built: [User.created_at.desc()]
    join_graph: JoinGraph  # With aliases and relationships
    select_related: List[str]
    prefetch_related: List[str]
    annotations: Dict[str, ColumnElement]  # Pre-built expressions
    having_conditions: List[ColumnElement]  # Pre-built
    # ... other configuration
```

**QueryCompiler (assembly only):**
```python
class QueryCompiler:
    def compile(self, state: QueryState):
        # Phase 1: Plan loading strategies
        directives = planner.plan(state.join_graph, context)

        # Phase 2: Assemble SQL from pre-built expressions
        stmt = self._build_select(state)
        stmt = self._apply_joins(stmt, state)
        stmt = self._apply_filters(stmt, state)  # Just wraps state.filters
        stmt = self._apply_ordering(stmt, state)  # Just wraps state.order_by
        stmt = self._apply_limit_offset(stmt, state)
        stmt = self._apply_distinct(stmt, state)
        stmt = self._apply_loading_options(stmt, state, directives)

        return stmt

    def _apply_filters(self, stmt, state):
        """Wrap pre-built filter expressions in WHERE clause."""
        if state.filters:
            stmt = stmt.where(and_(*state.filters))
        return stmt

    def _apply_ordering(self, stmt, state):
        """Wrap pre-built ordering expressions in ORDER BY."""
        if state.order_by:
            stmt = stmt.order_by(*state.order_by)
        return stmt
```

## Benefits of Separation

**1. Clear Responsibilities:**
- Each component has a single, well-defined job
- Easy to understand data flow
- No confusion about where logic belongs

**2. Independent Testing:**
```python
# Test filter parsing separately
def test_parse_lookup():
    field, lookup = parse_lookup("age__gte")
    assert field == "age" and lookup == "gte"

# Test field resolution separately
def test_resolve_field():
    column = resolve_field(User, "age")
    assert column == User.age

# Test condition building separately
def test_build_condition():
    expr = build_condition(User.age, "gte", 18)
    assert str(expr) == "user.age >= :age_1"

# Test compilation separately
def test_compile():
    state = QueryState(filters=[User.age >= 18])
    stmt = compiler.compile(state)
    assert "WHERE" in str(stmt)
```

**3. Easier Debugging:**
```python
# Inspect QueryState before compilation
print(f"Filters: {state.filters}")
print(f"Joins: {state.join_graph.nodes}")
print(f"Order: {state.order_by}")

# Then compile and inspect SQL
stmt = compiler.compile(state)
print(f"SQL: {stmt}")
```

**4. Optimization Opportunities:**
```python
# Compiler can optimize without touching expression building
def compile(self, state):
    # Analyze complete query state
    self._optimize_join_order(state.join_graph)
    self._choose_loading_strategies(state)

    # Then assemble optimized SQL
    return self._build_statement(state)
```

## Query Planning

The compiler's planning phase analyzes the complete query context to make loading strategy decisions:

**Planning Inputs:**
- Join graph structure (depth, cardinality)
- Query context (has aggregates, selected relationships)
- Configuration (max joinedload depth)

**Planning Outputs:**
- LoadDirectives for each relationship path
- Strategy: JOINEDLOAD, SELECTINLOAD, or SKIP
- Applied as SQLAlchemy loading options

**Planning Benefits:**
- Prevents N+1 queries automatically
- Chooses optimal loading strategy per relationship
- Respects depth limits to avoid cartesian explosions
- Adapts to query characteristics (aggregates, etc.)

## Performance Considerations

**Pipeline Overhead:**
- Expression building happens once during QuerySet construction
- Compilation happens once per query execution
- Total overhead: ~2-3ms for typical queries
- Negligible compared to database round-trip time

**Optimization Benefits:**
- Smart loading strategies prevent N+1 queries (saves 100s of ms)
- Join graph optimization reduces unnecessary JOINs
- Pre-built expressions enable query analysis
- Overall: Benefits far exceed pipeline overhead

## Consequences

**Positive:**
- Clean separation of concerns (SOLID principles)
- Each stage is independently testable
- Easy to debug - can inspect state at each stage
- Compiler focuses on SQL assembly, not expression logic
- Clear data flow from user input to SQL
- Optimization opportunities at multiple stages
- Easy to extend or modify individual components

**Negative:**
- More components than inline approach
- Need to understand multi-stage pipeline
- More files and classes to navigate
- Slight overhead from multiple stages

**Neutral:**
- Requires clear interfaces between stages
- Need documentation for each component
- Must maintain QueryState structure carefully

## Future Enhancements

- **Query caching:** Cache compiled statements for repeated queries
- **Query analysis:** Provide EXPLAIN output and optimization suggestions
- **Custom compilers:** Allow users to register custom compilation strategies
- **Query rewriting:** Transform inefficient patterns at compilation time
- **Batch compilation:** Compile multiple queries together for optimization
- **Expression optimization:** Simplify complex expressions before compilation

## Alternatives Considered

1. **Inline compilation:** Simpler but mixes all concerns, hard to test and optimize
2. **Compiler does everything:** Violates SRP, creates monolithic component
3. **Builder pattern:** Similar benefits but less flexible for optimization
4. **Visitor pattern:** Over-engineered for our needs
5. **Direct SQLAlchemy usage:** Loses Django-style API benefits
