# ADR-005: Filter Resolution Pipeline

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

The Django-style API (ADR-002) allows developers to specify filters using familiar lookups like `field__lookup` (e.g., `age__gte=18`). The QuerySet collects these high-level operations, but before the QueryCompiler (ADR-004) can assemble the SQL, these lookups need to be parsed, fields resolved to SQLAlchemy columns (potentially across relationships), and valid SQLAlchemy expressions constructed.

We need a robust mechanism to handle this transformation, ensuring correctness, supporting relationship traversal, and enabling JOIN optimization through proper context propagation.

## Decision

We will implement a three-stage pipeline for filter resolution that occurs during QuerySet operation collection:

1. **Filter Parser:** Orchestrates the complete kwargs-to-conditions pipeline
2. **Field Resolver:** Resolves field paths to SQLAlchemy columns and manages JOIN registration
3. **Condition Builder:** Constructs SQLAlchemy expressions using resolved columns, operators, and values

The pipeline transforms raw filter kwargs into pre-built SQLAlchemy expressions stored in QueryState, which the QueryCompiler later assembles into SQL.

## Pipeline Architecture

QuerySet.filter(status="active", price__gte=100)↓
QueryBuilder receives kwargs
    ↓
FilterParser.parse(kwargs, context)
    ↓
For each key-value pair:
    ↓
    FilterParser._parse_single(key, value, context)
        ↓FieldResolver.resolve_to_column(key, context)
            ↓
            - Split "price__gte" → field_path="price", lookup="gte"
            - Traverse relationships if needed
            - Register JOINs with JoinGraph
            - Return FieldResolution(column, lookup, join_node)
        ↓
        ConditionBuilder.build(column, lookup, value, join_node)
            ↓
            - Map lookup to SQLAlchemy operator
            - Handle special value types (F, QuerySet, Case)
            - Return SQLAlchemy expression
        ↓
        Return condition↓
Return list of conditions
    ↓
QueryBuilder updates QueryState.filters
    ↓
QueryCompiler wraps in WHERE clause


## Stage 1: Filter Parser

**Responsibility:** Orchestrate the complete kwargs-to-conditions transformation pipeline.

**Key Design:**
- Stateless coordinator - doesn't implement resolution or building logic
- Propagates ResolverContext through the pipeline for JOIN optimization
- Handles both simple fields (`status`) and lookup-style keys (`price__gte`)
- Lazy-initializes ConditionBuilder to avoid circular imports

**Input:**
```python
kwargs = {"status": "active", "price__gte": 100, "category__name__icontains": "elec"}
context = ResolverContext(mark_filter=True, in_or_context=False)
```

**Output:**
```python
[
    status == 'active',
    price >= 100,
    categories.name.ilike('%elec%')
]
```

**Context Propagation:**
The parser accepts a `ResolverContext` that controls JOIN optimization behavior:
- `mark_filter=True`: Marks JOINs as filter nodes (enables INNER JOIN promotion)
- `in_or_context=True`: Prevents INNER JOIN promotion for OR blocks
- `in_negation=True`: Marks JOINs to stay LEFT JOIN for NOT blocks

This context is propagated through the entire resolution chain, ensuring consistent JOIN behavior.

## Stage 2: Field Resolver

**Responsibility:** Resolve field paths to SQLAlchemy columns and manage JOIN registration.

**Key Design:**
- Splits lookup-style keys into field path and lookup operator
- Traverses relationships, registering JOINs with JoinGraph
- Returns structured FieldResolution with column, lookup, and join_node
- Validates field existence and relationship traversal

**Process:**
```python
# Input: "category__name__icontains"
# Step 1: Split → field_path=["category", "name"], lookup="icontains"
# Step 2: Start with Product model
# Step 3: Resolve "category" → Product.category relationship
#         - Register JOIN: Product → Category
#         - Get join_node from JoinGraph
# Step 4: Resolve "name" on Category → Category.name column
# Step 5: Return FieldResolution(
#             column=Category.name,
#             lookup="icontains",
#             join_node=<category_join_node>
#         )
```

**FieldResolution Structure:**
```python
@dataclass
class FieldResolution:
    column: ColumnElement  # SQLAlchemy column
    lookup: str  # Lookup operator ("icontains", "gte", etc.)
    join_node: JoinNode | None  # Reference to JOIN in graph
```

**JOIN Registration:**
The resolver doesn't build JOINs directly - it registers them with the JoinGraph, which manages aliases, deduplication, and topological ordering. The join_node reference allows the ConditionBuilder to mark filter usage for JOIN optimization.

## Stage 3: Condition Builder

**Responsibility:** Construct SQLAlchemy expressions from resolved columns, lookups, and values.

**Key Design:**
- Maps lookup operators to SQLAlchemy methods
- Handles special value types (F expressions, QuerySets, Case/When)
- Marks JOIN nodes as used by filters for optimization
- Returns ready-to-use SQLAlchemy boolean expressions

**Lookup Mapping:**
```python
"exact" → column == value
"gte" → column >= value
"lte" → column <= value
"gt" → column > value
"lt" → column < value
"in" → column.in_(value)
"contains" → column.contains(value)
"icontains" → column.ilike(f"%{value}%")
"startswith" → column.startswith(value)
"endswith" → column.endswith(value)
"isnull" → column.is_(None) if value else column.isnot(None)
"range" → column.between(value[0], value[1])
```

**Special Value Handling:**
```python
# F expressions
price__gt=F("cost") * 1.5
→ Product.price > Product.cost * 1.5

# QuerySets (subqueries)
category__in=Category.objects.filter(active=True)
→ Product.category_id.in_(SELECT id FROM categories WHERE active = true)

# Case/When expressions
status=Case(When(stock__lte=0, then="out"), default="available")
→ Product.status == CASE WHEN stock <= 0 THEN 'out' ELSE 'available' END
```

**Filter Marking:**
When building a condition, the builder marks the associated join_node (if any) as used by a filter. This enables the JoinGraph to promote LEFT JOINs to INNER JOINs during compilation, optimizing query performance.

## Integration with QueryBuilder

**QueryBuilder Role:**
The QueryBuilder acts as the entry point, receiving QuerySet operations and delegating to the appropriate pipeline.

**Context Determination:**
The QueryBuilder tracks query state (OR blocks, negations) and creates appropriate ResolverContext instances:
- Standard filters: `mark_filter=True`
- OR block filters: `mark_filter=True, in_or_context=True`
- NOT block filters: `mark_filter=True, in_negation=True`

## Interaction with QueryCompiler (ADR-004)

The pipeline produces pre-built SQLAlchemy expressions stored in QueryState. The QueryCompiler receives these expressions and wraps them into SQL:

```python
# FilterParser output stored in QueryState
state.filters = [
    Product.status == 'active',
    Product.price >= 100,
    Category.name.ilike('%elec%')
]

# QueryCompiler wraps in WHERE clause
stmt = select(Product)
stmt = stmt.where(and_(*state.filters))
```

The compiler doesn't parse lookups, resolve fields, or build conditions - it only assembles pre-built expressions into SQL structure.

## Design Principles

1. **Separation of Concerns:** Each stage has a single, clear responsibility
2. **Stateless Coordination:** FilterParser orchestrates without maintaining state
3. **Context Propagation:** ResolverContext flows through the entire pipeline
4. **Lazy Initialization:** ConditionBuilder constructed on first use to avoid circular imports
5. **Structured Output:** FieldResolution provides clear contract between stages
6. **JOIN Optimization:** Filter marking enables intelligent INNER JOIN promotion

## Error Handling

**Field Resolution Errors:**
```python
# Non-existent field
Product.objects.filter(invalid_field="value")
→ ModelAttributeError: "Product has no attribute 'invalid_field'"

# Invalid relationship traversal
Product.objects.filter(category__invalid__name="value")
→ ModelAttributeError: "Category has no attribute 'invalid'"
```

**Lookup Errors:**
```python
# Unsupported lookup
Product.objects.filter(price__invalid=100)
→ FilterError: "Unsupported lookup 'invalid' for field 'price'"

# Invalid value type
Product.objects.filter(price__in="not_a_list")
→ FilterError: "Lookup 'in' requires iterable value"
```

**Resolution Errors:**
```python
# Unexpected exception during resolution
→ FilterError: "Could not resolve field 'field_name': <original error>"
```

## Performance Characteristics

**Pipeline Overhead:**
- O(n) where n = number of filter kwargs
- Each kwarg requires:
  - O(1) key splitting
  - O(m) field resolution (m = relationship depth)
  - O(1) condition building
- Total: O(n × m) where m is typically 1-3

**Optimization Benefits:**
- Pre-built expressions avoid repeated resolution
- Filter marking enables INNER JOIN promotion (10-100x speedup)
- JOIN deduplication prevents redundant JOINs
- Context propagation ensures correct optimization in complex queries

## Consequences

**Positive:**
- Clear separation of parsing, resolution, and building logic
- Each stage independently testable
- Context propagation enables sophisticated JOIN optimization
- Structured FieldResolution provides clear stage contract
- Lazy initialization avoids circular import issues
- Extensible - new lookups added in one place (ConditionBuilder)
- Reusable - same pipeline for filter(), exclude(), Case/When

**Negative:**
- Three-stage pipeline adds conceptual complexity
- Multiple objects created per filter (FieldResolution, expressions)
- Context propagation requires careful tracking
- Circular import workaround needed for ConditionBuilder

**Neutral:**
- Requires understanding of ResolverContext semantics
- FieldResolution structure must be maintained carefully
- Error messages span multiple stages

## Future Enhancements

- **Custom Lookups:** Allow users to register custom lookup operators
- **Lookup Validation:** Validate lookup compatibility with field types
- **Expression Optimization:** Simplify complex expressions before building
- **Caching:** Cache FieldResolution for repeated field paths
- **Performance Profiling:** Track resolution time per field path
- **Better Error Messages:** Include field path context in all errors

## Alternatives Considered

1. **Single-stage resolution:** Simpler but mixes parsing, resolution, and building concerns
2. **Compiler handles resolution:** Violates SRP, makes compiler too complex
3. **Direct SQLAlchemy usage:** Loses Django-style API benefits
4. **Two-stage pipeline:** Combining parsing and resolution loses clarity
5. **Eager ConditionBuilder:** Causes circular import issues
