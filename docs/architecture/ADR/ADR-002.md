# ADR-002: Django-Style API Surface

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

With SQLAlchemy chosen as our foundation (see ADR-001), we needed to decide on the API surface that developers would
interact with. SQLAlchemy's ORM API is powerful but verbose with a steep learning curve. We needed an interface that
would be intuitive, maintainable, and familiar while preserving SQLAlchemy's power.

## Decision

We will implement a Django-style declarative API surface that mimics Django ORM's patterns, providing a familiar
interface on top of SQLAlchemy's foundation.

## Rationale

**Why Django-Style API:**

- Django ORM is one of the most widely used ORMs in Python
- Most Python developers have experience with Django's patterns
- Significantly reduces onboarding time for new team members
- Existing Django knowledge transfers directly
- Cleaner, more readable code compared to SQLAlchemy's imperative style
- Chainable QuerySet API feels natural for query building

**Code Readability Comparison:**

```python
# Our Django-style API
users = await User.objects.filter(
    age__gte=18,
    email__contains='@example.com'
).select_related('profile').all()

# vs SQLAlchemy's API
users = await session.execute(
    select(User)
    .where(User.age >= 18)
    .where(User.email.contains('@example.com'))
    .options(joinedload(User.profile))
).scalars().all()
```

**Why Not SQLAlchemy's API Directly:**

- Verbose and complex (e.g., `session.query(Model).filter(Model.field == value)`)
- Steep learning curve for developers unfamiliar with SQLAlchemy
- Code becomes harder to read and maintain at scale
- Relationship loading behavior is less intuitive
- Requires understanding of SQLAlchemy's session mechanics

## Performance Considerations

The architecture is intended to reduce unnecessary relationship loading and
provide a predictable query-planning pipeline. No reproducible benchmark dataset
or benchmark harness was included with the extracted source, so this ADR makes
no quantitative latency or throughput claims. Performance characteristics must
be measured with reproducible benchmarks before being presented as guarantees.

**Expected trade-offs:**

- Query compilation and validation add CPU work before SQL execution.
- Explicit eager-loading controls can reduce N+1 query patterns when used correctly.
- Join planning can improve or worsen a query depending on relationship shape and
  database statistics; each optimization must be validated against real SQL plans.

## API Components

**Model Layer:**

- `Model` base class with metaclass magic
- SQLAlchemy `Column` definitions directly on models (no custom field wrappers)
- Relationship definitions using SQLAlchemy's `relationship()`
- Model methods: `save()`, `delete()`, `refresh()`

**Manager Layer:**

- `Manager` class attached to models as `objects`
- Entry point for queries: `Model.objects.filter(...)`
- Custom manager support for reusable query logic

**QuerySet Layer:**

- Chainable query methods: `filter()`, `exclude()`, `annotate()`, `order_by()`
- Relationship loading: `select_related()`, `prefetch_related()`
- Aggregation: `count()`, `values_list()`
- Execution methods: `all()`, `first()`, `get()`, `exists()`

**Lookup System:**

- Django-style field lookups: `field__lookup`
- Supported lookups: `exact`, `iexact`, `contains`, `icontains`, `gt`, `gte`, `lt`,
  `lte`, `in`, `not__in`, `isnull`, `startswith`, `endswith`, `range`, and `between`.
- Additional SQLAlchemy predicate operators are explicitly allowlisted; arbitrary
  column methods such as `asc()`, `desc()`, `op()`, and `label()` are not filter lookups.
- Relationship traversal: `profile__user__email__contains`

## Design Principles

1. **Familiarity over novelty:** Use Django patterns developers already know
2. **Explicit over implicit:** Require explicit relationship loading
3. **Readable over concise:** Prioritize code clarity
4. **Chainable over nested:** Enable method chaining for query building
5. **Async-first:** All query methods are async by default

## Deviations from Django

While we mimic Django's API, we make intentional improvements:

1. **Async-first:** All methods are async, not retrofitted
2. **Explicit sessions:** Pass session explicitly, no thread-local magic (see ADR-003)
3. **Type hints:** Full type annotation support for better IDE experience
4. **No implicit transactions:** Transactions must be explicit
5. **Stricter relationship loading:** No lazy loading fallback
6. **SQLAlchemy columns:** Use SQLAlchemy `Column` directly instead of custom field classes
7. **No aggregate() method yet:** Use `annotate()` for aggregations (aggregate() planned for future)

## Consequences

**Positive:**

- Familiar API reduces learning curve dramatically
- Clean, readable code that's easy to maintain
- Explicit relationship loading prevents performance pitfalls
- Chainable QuerySet enables elegant query composition
- Lower cognitive load for developers
- Easy to write and understand complex queries
- Direct SQLAlchemy column usage reduces abstraction layers

**Negative:**

- Developers familiar only with SQLAlchemy need to learn Django patterns
- Some SQLAlchemy power features may be harder to access
- Query parsing and compilation add overhead; the magnitude has not been measured
- Must maintain API compatibility as we evolve
- Missing some Django ORM features (aggregate(), custom field types)

**Neutral:**

- Need comprehensive documentation for API surface
- Must carefully design API to avoid future breaking changes
- Some edge cases may require dropping down to SQLAlchemy
- Future work needed for full Django ORM feature parity

## Examples

**Basic Queries:**

```python
# Simple filter
users = await User.objects.filter(age__gte=18).all()

# Chaining
active_users = await User.objects.filter(
    is_active=True
).exclude(
    email__isnull=True
).order_by('-created_at').all()

# Relationship traversal
posts = await Post.objects.filter(
    author__profile__country='US'
).select_related('author', 'author__profile').all()
```

**Annotations (for aggregation):**

```python
from sqlalchemy import func

# Count posts per user
users = await User.objects.annotate(
    post_count=func.count(Post.id)
).filter(post_count__gt=10).all()

# Average age
users = await User.objects.annotate(
    avg_age=func.avg(User.age)
).all()
```

## Performance Validation

No measured performance benchmarks are currently published. A reproducible
benchmark suite is required before performance claims are added to public docs.

## Future Enhancements

- Custom field types (CharField, IntegerField, etc.) for better Django compatibility
- `aggregate()` method for simpler aggregation syntax

## Alternatives Considered

1. **SQLAlchemy's native API:** Too verbose, steep learning curve
2. **Custom novel API:** Would require extensive documentation and training
3. **Peewee-style API:** Less familiar to most developers
4. **Active Record pattern:** Less flexible than QuerySet pattern
5. **Repository pattern:** More boilerplate, less intuitive for simple cases
