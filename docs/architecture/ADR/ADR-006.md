# ADR-006: Join Graph for Relationship Management

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

When translating Django-style relationship filters like `category__parent__name="Electronics"` into SQLAlchemy queries, we need to manage JOIN operations carefully. Naive approaches lead to several problems:

- **Duplicate JOINs:** The same relationship path might be referenced multiple times (in filters, annotations, order_by), causing redundant JOIN clauses
- **Incorrect JOIN order:** SQLAlchemy requires JOINs to appear in dependency order (parent tables before child tables)
- **JOIN type confusion:** Some JOINs should be LEFT (preserve null relationships), others INNER (filter requires non-null), and the decision depends on usage context
- **Complex traversal:** Deep relationship chains like `building__city__country__continent` require tracking multiple levels of dependencies

Without a centralized structure to manage these concerns, the query compiler becomes complex and error-prone.

## Decision

We implement a **JoinGraph** data structure that maintains a directed acyclic graph (tree) of JOIN operations. The graph:

1. **Tracks all JOINs as a tree structure** with a synthetic root node representing the base model's FROM clause
2. **Ensures topological ordering** so parent JOINs always appear before child JOINs in SQL emission
3. **Prevents duplicate JOINs** by registering paths once and merging usage flags on re-registration
4. **Manages JOIN types** (LEFT vs INNER) with promotion support based on usage context
5. **Provides tree traversal utilities** for query planning and optimization passes

## Architecture

**Core Components:**

| Component | Responsibility |
|-----------|---------------|
| JoinGraph | Central registry and tree manager |
| JoinNode | Individual JOIN with metadata and tree links |
| Path Registry | O(1) lookup by relationship path |
| Join Order | Topologically sorted list for SQL emission |

**Key Operations:**

1. **add_node(path, ...flags)** - Register or update a JOIN path with usage tracking
2. **get_node(path)** - Retrieve existing JOIN node
3. **join_order** - Get topologically sorted JOINs for SQL emission
4. **set_join_type(path, type)** - Promote JOIN type (used by optimization passes)

**Tree Structure:**

<root> (Product)
├── category [LEFT]
│   └── parent [INNER] [filter]
└── supplier [LEFT]
    └── country [LEFT] [filter]


Each node tracks:
- Path (e.g., "category__parent")
- SQLAlchemy alias and relationship
- JOIN type (LEFT/INNER)
- Usage flags (filter, or_context, nullable_check, negation, order_by, annotation)
- Parent/children links

## Benefits

**Correctness:**
- Topological ordering guarantees valid SQL
- Tree structure prevents cycles
- Usage flag merging ensures conservative optimization

**Performance:**
- O(1) path lookup via dictionary
- O(d) node addition where d = depth
- Eliminates duplicate JOINs automatically

**Maintainability:**
- Single source of truth for JOIN state
- Clear separation from query compilation logic
- Supports optimization passes via clone()

**Developer Experience:**
- Automatic ancestor creation (adding "a__b__c" creates "a" and "a__b")
- ASCII tree visualization for debugging
- Validation utilities catch graph corruption

## Usage Flags

The graph tracks why each JOIN is needed:

- `used_in_filter` - Referenced in WHERE clause (enables LEFT→INNER promotion)
- `used_in_or_context` - Inside OR clause (prevents promotion)
- `has_nullable_check` - IS NULL/IS NOT NULL check (prevents promotion)
- `used_in_negation` - Inside NOT/exclude() (prevents promotion)
- `used_in_order_by` - Referenced in ORDER BY (keeps JOIN)
- `used_in_annotation` - Referenced in annotate() (keeps JOIN)

Flags use OR semantics: once True, they stay True. This ensures conservative optimization.

## Integration Points

**Filter Resolution:**
- FieldResolver calls `graph.add_node()` when traversing relationship paths
- Registers usage flags based on filter context (OR, negation, etc.)

**Query Compilation:**
- QueryCompiler iterates `graph.join_order` to emit JOIN clauses
- Uses node.join_type to determine LEFT vs INNER
- Accesses node.alias for table references

**Query Planning:**
- JoinPromotionPass analyzes usage flags and calls `graph.set_join_type()`
- LoadingStrategyPass reads graph to decide joinedload vs selectinload
- Graph provides clone() for experimental optimization

## Alternatives Considered

**Flat JOIN list:** Simpler but requires manual topological sorting and duplicate detection. Rejected due to complexity in maintaining correct order.

**Implicit JOIN tracking in QueryState:** Couples JOIN management with query state. Rejected for poor separation of concerns.

**SQLAlchemy's built-in JOIN tracking:** Doesn't provide Django-style path semantics or usage flag tracking. Rejected as insufficient for our needs.

## Future Enhancements

- Cycle detection (currently prevented by tree structure)
- JOIN reordering optimization based on cardinality estimates
- Automatic INNER JOIN promotion based on NOT NULL constraints
- Visualization export (DOT format for Graphviz)
