# ADR-007: Query Planning Pipeline for Optimization

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

After building the QuerySet API, filter resolution pipeline, and join graph, we have all the components needed to construct SQLAlchemy queries. However, naively translating user intent into SQL leads to performance problems:

- **Inefficient JOINs:** LEFT JOINs used everywhere when INNER would be faster and more correct
- **GROUP BY expansion:** Using `joinedload` with aggregates forces all joined columns into GROUP BY, slowing queries and producing incorrect counts
- **Cartesian products:** Multiple collection `joinedload` operations from the same parent multiply row counts exponentially
- **Excessive JOIN depth:** Deep relationship chains like `a__b__c__d__e` create wide SELECT statements with many columns
- **Redundant loads:** Loading relationships already materialized by filter JOINs wastes query time

Without optimization, queries work but perform poorly at scale.

## Decision

We implement a **Query Planning Pipeline** that optimizes queries before execution. The planner:

1. **Runs optimization passes in sequence** - each pass receives directives from the previous pass
2. **Operates on LoadDirectives** - abstract representation of loading strategies (joinedload, selectinload, skip)
3. **Mutates the JoinGraph** - only the JoinPromotionPass can modify JOIN types through a narrow interface
4. **Produces audit trails** - explains what each pass did for debugging

The pipeline uses the Strategy + Chain of Responsibility pattern, allowing passes to be added, removed, or reordered without touching other code.

## Architecture

**Core Components:**

| Component | Responsibility |
|-----------|---------------|
| QueryPlanner | Orchestrates pass execution and threads state |
| PlanningPass | Abstract interface for optimization passes |
| LoadDirective | Represents a loading strategy for a relationship path |
| PassResult | Contains directives, warnings, and mutations from a pass |

**Standard Pipeline Order:**

1. **JoinPromotionPass** - Promotes LEFT → INNER for filter-mandated JOINs
2. **AggregateStrategyPass** - Demotes joinedload → selectinload when aggregates present
3. **DepthSplittingPass** - Splits deep joinedload chains (head stays joined, tail uses selectin)
4. **CartesianDetectionPass** - Demotes sibling collection joinedloads to prevent row multiplication
5. **RedundantPathPass** - Skips paths already materialized or covered by longer paths

## Planning Passes

**JoinPromotionPass:**
- Only pass that mutates the JoinGraph
- Promotes LEFT → INNER when safe (filter-mandated, no OR context, no nullable checks)
- Validates ancestor chain supports INNER (can't have LEFT parent with INNER child)
- Uses narrow `JoinGraphMutable` interface for controlled mutation

**AggregateStrategyPass:**
- Detects queries with aggregates (COUNT, SUM, etc.)
- Demotes all joinedload → selectinload to prevent GROUP BY expansion
- Prevents incorrect counts from cartesian products with joined tables

**DepthSplittingPass:**
- Configurable max depth (default: 2)
- Splits paths like `a__b__c__d` into `a__b` (joinedload) + `c` (selectinload) + `d` (selectinload)
- Prevents excessively wide SELECT statements

**CartesianDetectionPass:**
- Groups collection joinedloads by parent path
- Keeps first collection as joinedload, demotes rest to selectinload
- Example: Parent with books + reviews → books stays joined, reviews uses selectin

**RedundantPathPass:**
- Skips paths already in join graph (filter already joined that table)
- Skips prefix paths covered by longer loads (`a__b` covered by `a__b__c`)
- Final cleanup pass

## Benefits

**Performance:**
- INNER JOINs enable better query plans and index usage
- Prevents GROUP BY expansion with aggregates
- Avoids cartesian products from multiple collections
- Reduces SELECT width from deep joins

**Correctness:**
- Aggregate queries produce accurate counts
- JOIN promotion respects OR context and nullable checks
- Ancestor validation prevents invalid JOIN combinations

**Maintainability:**
- Passes are independent and composable
- Easy to add new optimization passes
- Clear separation from query compilation
- Audit trail explains optimization decisions

**Debuggability:**
- `planner.explain()` shows what each pass did
- Warnings highlight potential issues
- Mutations tracked for transparency

## Integration

**Query Execution Flow:**

1. User calls `queryset.filter(...).select_related(...)`
2. QueryBuilder builds QueryState with filters and join graph
3. QueryPlanner receives graph and context
4. Planner runs passes in sequence
5. Final LoadDirectives passed to QueryCompiler
6. Compiler applies loading strategies to SQLAlchemy query

**Example:**

```python
# User query
products = (
    Product.objects
    .filter(category__parent__name="Electronics")
    .select_related("category__parent__grandparent", "supplier__country")
    .annotate(review_count=Count("reviews"))
)

# Planning pipeline:
# 1. JoinPromotionPass: category__parent LEFT→INNER (filter-mandated)
# 2. AggregateStrategyPass: All joinedloads→selectinload (COUNT present)
# 3. DepthSplittingPass: category__parent__grandparent split at depth 2
# 4. CartesianDetectionPass: No sibling collections
# 5. RedundantPathPass: category__parent skipped (already in graph)
```

## Pass Protocol

Each pass implements:

```python
class PlanningPass:
    name: str

    def execute(
        self,
        graph: JoinGraphReadable,
        context: QueryContext,
        current_directives: List[LoadDirective],
    ) -> PassResult:
        ...
```

**Inputs:**
- `graph` - Read-only view of join graph (except JoinPromotionPass gets mutable)
- `context` - Query metadata (has_aggregates, select_related_paths, etc.)
- `current_directives` - Output from previous pass

**Output:**
- `PassResult` with new directives, warnings, and mutations

## Alternatives Considered

**Optimization in QueryCompiler:** Couples optimization with SQL generation. Rejected for poor separation of concerns.

**Single monolithic optimizer:** Hard to test and extend. Rejected in favor of composable passes.

**No optimization:** Simpler but produces slow queries. Rejected as unacceptable for production use.

**Heuristic-based optimization:** Complex rules hard to reason about. Rejected in favor of explicit passes with clear responsibilities.

## Future Enhancements

- Cost-based optimization using table statistics
- Subquery materialization for complex filters
- Index hint injection
- Query result caching based on plan fingerprint
- Parallel pass execution for independent optimizations
- Machine learning for adaptive optimization
