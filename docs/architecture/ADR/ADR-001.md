# ADR-001: SQLAlchemy as Foundation Layer

**Status:** Accepted
**Date:** 2026-03-30
**Deciders:** Project maintainers

## Context

Building a production-grade ORM from scratch requires solving complex problems: SQL generation, connection pooling, transaction management, dialect differences, type mapping, and query optimization. We needed to decide whether to build everything from the ground up or leverage an existing foundation.

## Decision

We will use SQLAlchemy Core and ORM as the foundation layer for SQL generation, connection management, and database abstraction.

## Rationale

**Why SQLAlchemy:**
- Battle-tested SQL generation and dialect support (PostgreSQL, MySQL, SQLite, Oracle, MSSQL)
- Robust connection pooling and transaction management
- Async support via `sqlalchemy.ext.asyncio`
- Comprehensive type system and schema introspection
- Feature-rich query capabilities (CTEs, window functions, subqueries, lateral joins)
- Active maintenance and large community (15+ years of development)
- Production-proven at scale

**Why Not Build from Scratch:**
- SQL generation is extremely complex across different database dialects
- Database-specific quirks and edge cases require years of refinement
- Connection pooling and transaction handling are error-prone
- Would take 2+ years to reach SQLAlchemy's maturity and feature parity
- Reinventing the wheel diverts resources from our actual value proposition

## Consequences

**Positive:**
- Immediate access to mature, production-ready SQL generation
- Support for multiple databases out of the box
- Reduced development time (focus on API design, not SQL internals)
- Leverage SQLAlchemy's performance optimizations and query planning
- Strong type safety via SQLAlchemy's type system
- Async/await support for modern Python applications
- Comprehensive documentation and community resources

**Negative:**
- External dependency (version compatibility, security updates)
- Learning curve for contributors (need SQLAlchemy knowledge)
- Some SQLAlchemy complexity may leak through in edge cases
- Limited by SQLAlchemy's capabilities and design decisions
- Must track SQLAlchemy releases and migration paths

**Neutral:**
- Must maintain compatibility with SQLAlchemy major versions
- Need to wrap SQLAlchemy exceptions in our own exception hierarchy
- Query compilation translates our API to SQLAlchemy constructs

## Implementation Notes

- Use SQLAlchemy 2.0+ for modern async support and improved type hints
- Wrap `AsyncSession` for session management
- Map our field types to SQLAlchemy column types
- Use SQLAlchemy's `select()` construct as compilation target
- Leverage SQLAlchemy's connection pooling and engine management

## Alternatives Considered

1. **Build from scratch:** Too time-consuming, would reinvent the wheel, 2+ years to maturity
2. **Use Django ORM directly:** Not async-native, tightly coupled to Django framework, less powerful query capabilities
3. **Use Tortoise ORM:** Less mature, smaller community, limited features, fewer database dialects
4. **Use Peewee:** Synchronous only, less powerful query API, smaller ecosystem
5. **Use SQLModel:** Too opinionated, Pydantic coupling, less flexible for our needs
